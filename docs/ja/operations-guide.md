# 運用・トラブル対応

[ドキュメント一覧](README.md) | [利用者ガイド](user-guide.md)

## 開演前の確認

1. 前回正常に動作した`config.json`をバックアップします。
2. 実行ファイルと`static/`があるディレクトリから起動します。
3. コントロール画面で予定したグループ名を確認します。
4. Browser onlyのON／OFFを確認します。外部制御を使う場合はOFFにします。
5. 物理機器のアドレスとモードを設定のチャンネル配置に照合します。
6. グループごとにFade In、Fade Out、Cutを試し、実際の灯体を確認します。
7. OSCを使う場合は、対象のミキサーチャンネルでMute／Unmuteを確認します。
8. 外部制御を使う場合は、その制御ソフトウェアからも操作します。

ヘルスチェック成功はHTTPサーバーが応答したことを示します。
DMX機器やミキサーが接続され、正しく動作することの確認とは分けてください。

## 状態表示の読み方

| 表示 | 意味 | 次に確認すること |
| --- | --- | --- |
| 出力の割合 | 設定済み最大値に対するソフトウェア出力の割合 | 実際の灯体の明るさと一致するか |
| `waiting` | 開始遅延の待機中 | コマンドの`interval` |
| `fading` | フェードが進行中 | `duration`と`dmx.fadeInterval` |
| `idle` | 待機・進行中のフェードがない | 出力は0とは限らない |
| `Muted` / `Unmuted` | 最後にOSC送信を完了した要求 | ミキサー側の実際の状態 |
| `State unavailable` | 状態を取得できない、またはOSCの状態が未確定 | 接続・ログ・OSCの送信先 |

出力割合はフェードの進捗率ではありません。例えば最大値128のdimmerが128を出力すると100%です。
ミキサー本体を直接操作しても、その結果がDMXBOXへ返ってくるわけではありません。

## 手動操作へ切り替える

1. 設定画面下部の**Control mode**を開きます。
2. **Browser only**をONにします。Updateは不要です。
3. 操作画面でもONを確認し、ブラウザーから必要な操作を行います。
4. 外部制御側のコマンド送信を止め、原因を確認します。
5. 外部制御へ戻す準備ができたらOFFにし、単発の操作で復帰を確認します。

このモードはTCPなどからのFade／Mute要求を制限します。入力を制限する機能であり、
すでに実行中のフェードを停止したり、出力をブラックアウトしたりする機能ではありません。
再起動すると解除されます。認証やアクセス権の管理にも使用できません。

## 操作ログを確認する

アプリのメニューから**Operation Log**を開きます。
最近100件を新しい順で表示し、2秒ごとに更新します。

| 列 | 内容 |
| --- | --- |
| Time | 操作を記録した時刻。画面ではブラウザーのローカル時刻で表示 |
| Source | 入力元モジュール。例：`http`、`tcp` |
| Target | 出力先モジュール。例：`dmx`、`osc` |
| Action | `fade`、`mute` |
| Arguments | グループID、方向、時間などの要求内容 |

ログは内部モジュールへ要求を渡した時点の記録です。
フェード完了や物理機器の応答を記録したものではありません。
同時刻の標準出力ログと組み合わせて原因を調べてください。

カレントディレクトリの`operations.jsonl`へ1行1件のJSONで追記します。
起動時にはファイルから最近の履歴を読み込み、メモリーでは最大1000件を保持します。
自動ローテーションはありません。長期運用ではサイズを確認し、停止中に退避してください。
ファイルを開けない場合のエラーは標準出力ログで確認します。

## 症状から切り分ける

| 症状 | 確認する順序 |
| --- | --- |
| グループが表示されない | 起動ディレクトリ → 読み込んだ設定 → `dmx.groups` → 保存後の再起動案内 |
| ゲージは動くが灯体が変わらない | 有効な出力 → ポート／宛先 → 灯体のチャンネルとモード → 配線 |
| Fadeがすぐ終わる | Cutを押していないか → `duration:0` → `fadeInterval` |
| 外部制御だけ動かない | Browser only → TCPモジュールの有効化 → 再起動 → 待受ポート → 改行区切り |
| Mute表示が不明のまま | OSC有効化 → 再起動 → チャンネル一覧 → 送信エラー |
| 保存後に画面の接続が切れた | HTTP待受の変更 → 新しいURL → 再読み込み → 標準出力ログ |
| 起動のたびに設定が戻る | 作業ディレクトリ → 対象の`config.json` → ファイルの書き込み権限 |

TCPの`ack`やHTTPの`result: OK`だけで、機器の動作成功とは判断できません。
詳しくは[TCPプロトコル仕様](tcp-protocol.md)と[HTTP API・外部連携](http-api.md)を参照してください。

## 設定変更と復旧

本番中の出力先やグループ構成の変更は、接続の作り直しや出力状態の初期化を伴う可能性があります。
変更前に機器側の状態を確認し、操作を止められる時間帯に実施してください。

保存時に再起動が必要と表示された場合は、保存された設定と稼働中の設定が一致していると考えず、
再起動後にグループ・出力先・外部制御を再確認します。
問題が続く場合は、プロセスを停止し、バックアップの`config.json`を戻してから起動します。

終了時にブラックアウトフレームを明示送信する実装ではありません。
必要なFade Outや機器側の操作を行ってから終了し、信号断時の挙動も確認してください。

## 不具合報告に添える情報

- 使用したリリース、OS、機器・アダプター名
- 発生時刻と再現手順、期待した結果と実際の結果
- 関連する標準出力ログと操作ログ
- 個人情報や内部ネットワーク情報を除いた設定
- ブラウザー操作／HTTP／TCPのどれで発生したか
- console出力だけでも再現するか、実機接続時だけか

設定やログを公開するときは、IPアドレス、機材名、運用情報の扱いを確認してください。
